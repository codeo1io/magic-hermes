# Magic-Hermes v0.3.29 — parallel bind-lock safety

This release ships the Magic Context bridge mutex fix from PR #101. Hermes
subagents previously encountered shared SQLite `database is locked` failures
and, in some concurrent startup races, `ENOENT` writing
`context.db.bindlock/pid`. The bridge's lock was under scratch storage,
an unpublished PID was treated as a dead owner, age alone could evict a
live owner, and retry backoff held the lock.

The bridge now places its bind mutex beside the durable context database,
allows a bounded PID-publication grace, never evicts a live holder merely
because it is old, and releases the mutex before retry cooldown. The
shared database is not migrated or deleted by this change.

## Validation and rollout

PR #101 and version PR #102 both passed pinned Magic Context CI, including
Node syntax and Ruff. The release script's full local battery passed
387 tests (2 skipped) and built wheel/sdist for v0.3.29. Publication is
separate from live activation. Before activating in Hermes, verify the
running sessions and spool child ownership; avoid restarting a service
that owns active Pi sessions. After activation, compare Magic Context
bind errors, concurrent subagent progress, and DB availability against
pre-deployment evidence. If regressions appear, restore the previously
installed wheel/config using the established release rollback path.

**Migration status:** This fixes a concrete concurrency defect but does
not certify the native-rails migration, M5 recovery, or unattended soak.
